# Правила написання коду та здачі ДЗ (CONTRIBUTING)

Для спрощення перевірки та підтримання високої якості коду, на курсі діють наступні правила.

## 1. Типи даних (ОБОВ'ЯЗКОВО)

Заборонено використовувати базові типи C/C++ зі змінною розмірністю, якщо це не вимагається сторонніми API.
Всі типи мають бути явно вказані через `<stdint.h>`.

**ПРАВИЛЬНО:**
```c
#include <stdint.h>

uint8_t   counter = 0;
int32_t   temperature = -25;
uint32_t  timestamp = 0;
```

**НЕПРАВИЛЬНО:**
```c
int counter = 0;          // Заборонено
long int temperature;     // Заборонено
unsigned char buffer[10]; // Заборонено
```

## 2. Код-стайл та Іменування

1.  **Змінні та функції:** Використовуйте зрозумілі назви.
    *   Змінні: `snake_case` (напр. `sensor_value`).
    *   Функції: `camelCase` (напр. `readSensorValue()`) або `snake_case` за домовленістю з ментором. Відповідно до `.clang-tidy` налаштовано `camelCase` (але можна змінити).
2.  **Структури та Енуми:** `CamelCase` (напр. `SensorData`).
3.  **Макроси та Константи:** `UPPER_CASE_WITH_UNDERSCORES` (напр. `MAX_BUFFER_SIZE`).
4.  **Форматування:** Використовується `clang-format`. Заборонено робити комміти з невідформатованим кодом. Встановіть розширення Clang-Format для своєї IDE.

## 3. Оформлення Pull Request (PR)

1.  **Одна гілка = одне ДЗ.** Не мішайте декілька завдань в одну гілку. Назва гілки має **обов'язково співпадати** з назвою папки домашньої роботи (наприклад, гілка `hw_1.1` і папка `hw_1.1`, або гілка `hw_miniproject_1` і папка `hw_miniproject_1`).
2.  **Назва PR** має бути інформативною, наприклад: `hw_1.1: Led Blink`.
3.  **Опис PR (Description):**
    *   Коротко опишіть, що було зроблено.
    *   Якщо є якісь нетипові рішення — поясніть їх.
    *   Додайте скріншот або лог виводу терміналу, якщо це доречно.
4.  Сам код буде перевірятися ментором, а також (в деяких випадках) штучним інтелектом. Пишіть код чисто, залишайте коментарі для складної логіки.
5.  Не залишайте "мертвого" (закоментованого) коду. Видаляйте його перед відкриттям PR.

## 4. Структура проєкту та використання автогенераторів (CubeMX)

Щоб полегшити перевірку коду ментором та ШІ, **весь ваш власний код має бути ізольований від згенерованого коду (бібліотек, HAL тощо).**

1. **PlatformIO:**
   * Ваш код має знаходитись у папках `src/` та `include/`.
   * Будь-які сторонні бібліотеки та HAL — у папці `lib/`.
2. **STM32CubeMX / CubeIDE:**
   * Згенеровані папки `Drivers/`, `Core/`, `Middlewares/` **не перевіряються**.
   * Власну логіку пишіть виключно у створеній вами папці `App/` або `Sources/`.
   * Файли на кшталт `stm32f4xx_hal_msp.c`, якщо ви вносите туди зміни, також переносьте у `lib/` або чітко ізолюйте.
